
원칙 A. 평탄성(Flatness)
독립적인 옵션의 나열 순서가 의미를 바꾸어서는 안 된다.
tool users --active --role admin
tool users --role admin --active


두 명령은 같은 결과를 내야 해.
형식적으로 조건 \(A, B\)에 대해 다음이 성립해야 한다는 뜻이야.
\[
\operatorname{eval}(A,B)=\operatorname{eval}(B,A)
\]

이를 순서 독립성(order independence)이라고도 볼 수 있어.
단, 모든 CLI 인자가 순서와 무관해야 한다는 뜻은 아니야. 파이프라인 단계나 순서가 중요한 인자는 별도로 정의할 수 있어.
원칙 B. AND 의미론(Conjunctive Semantics)
일반적인 필터 옵션은 기본적으로 모두 만족해야 하는 조건으로 해석한다.
tool users --active --role admin --age-min 20


논리식으로 표현하면 다음과 같아.
\[
A \land B \land C
\]

즉, 활성 상태이고, 관리자 역할이며, 나이가 20세 이상인 사용자를 조회해.
여기서 중요한 점은 --active, --role, --age-min이 각각 독립된 조건이라는 것이야. 사용자가 옵션을 나열한 순서나 옵션 사이에 숨겨진 우선순위는 없어.

2. 그러면 OR 조건은 어떻게 표현할까?
핵심은 일반 필터 나열 문법에 OR 연산자를 섞지 않는 것이야. OR가 필요하면 그 의미를 명시적으로 표현하는 별도 문법을 사용하면 돼.

방법 1. 같은 옵션을 반복해 OR 표현
tool users --role admin --role manager


--role의 반복은 값 사이의 OR, 서로 다른 옵션 사이의 AND로 정의하는 방식이야.
\[
(\text{role=admin} \lor \text{role=manager})
\]

단, 반복 옵션이 OR를 뜻한다는 규칙을 명세에 명시해야 해.



같은 옵션을 반복해 OR 표현






cli 인터페이스는 좌측에서 우측으로 읽는 1차원 언어이다

### 1. 질문에 대한 직접적인 답 (Identity Element)

> **"OR로 합성할 때, 옵션을 아무것도 지정하지 않았을 때의 기본값(Identity Element)은 무엇을 해야 하는가?"**

* **`AND` 결합일 때:**
* 기본값 = **$\top$ (True / 전체 집합)**
* 옵션 0개일 때 "모든 대상을 조회"합니다. 옵션을 추가할 때마다 범위가 줄어듭니다 ($A \land \top = A$). ➔ **자연스러움**


* **`OR` 결합일 때:**
* 기본값 = **$\bot$ (False / 공집합)**
* 옵션 0개일 때 "아무것도 조회하지 않음"이어야 대수적으로 성립합니다 ($A \lor \bot = A$).
* 하지만 옵션을 안 줬는데 결과가 0개 나오는 CLI는 상식(전체 조회)에 반합니다.
* 만약 기본값을 '전체 조회($\top$)'로 둔 채 `OR`를 쓰면, $A \lor \top = \top$이 되어 **모든 옵션이 무력화되는 모순**이 생깁니다.


## 옵션 설계

### 순서 독립성 (Order Independence / Flatness)

독립적인 옵션의 나열 순서가 의미를 바꾸어서는 안 된다 ($\operatorname{eval}(A, B) = \operatorname{eval}(B, A)$).

### 나열된 옵션은 왜 AND 조건이어야 하는가?

1. **대수적 이유 (Identity Element와 기본값의 일치)**
* **`AND` 나열:** 0개 옵션의 항등원은 $\top$ (전체 집합)이다. 옵션을 지정하지 않으면 모든 대상을 보여주고, 옵션을 덧붙일수록 범위가 조여든다 ($\text{Filter} \land \top = \text{Filter}$).
* **`OR` 나열:** `OR` 연산의 항등원은 $\bot$ (공집합)이다. 기본값을 '전체 조회($\top$)'로 둔 채 `OR`로 합성하면 $\text{Filter} \lor \top = \top$이 되어 모든 옵션이 무시되는 대수적 모순이 발생한다.


2. **인지적 이유 (제약 조건의 누적)**
* 공백에 의한 나열(Juxtaposition)은 인간 언어에서 '제약 조건의 누적(Accumulation of Constraints)'이다.
* **자연어:** *"빨간색, 250 사이즈, 운동화 보여줘"* $\rightarrow$ 당연히 `빨간색 AND 250 AND 운동화`를 의미한다.
* 옵션을 덧붙일수록 검색 결과가 늘어나는 것(`OR`)은 인간의 자연스러운 조건 축소 직관을 위반한다.

> or 조건을 표현하면서도 복잡도가 올라가지 않으면서 가장 좋은 방법은 동일한 옵션 반복은 or 조건으로 하는것이다

# CLI 명령어 구조의 2가지 해석 모델: 작동적 파이프라인과 형식 의미론

---

## 1. 근본적인 형식 의미론 모델 (Architecture View)

형식 언어론과 유닉스 CLI 구조 관점에서 모든 CLI 옵션은 본질적으로 `[대상 지정]`과 `[행위 지정]`이라는 2가지 통사 범주(Syntactic Category)로 환원됩니다.

$$\text{CLI World} = \underbrace{\text{Predicate (명사 / 조건절)}}_{\text{대상 지정: } D \to \text{Bool}} \;+\; \underbrace{\text{Action (동사 / 처리)}}_{\text{행위 지정: } \text{State} \to \text{State}}$$

```
       ┌────────────────────────────┐
       │   CLI 명령어의 세계관       │
       └──────────────┬─────────────┘
                      │
         ┌────────────┴────────────┐
         ▼                         ▼
   [1. 대상 지정]            [2. 행위 지정]
  (Predicate / Query)     (Action / Computation)
   = 명사 / 조건절           = 동사 / 처리

```

### ① [대상 지정] 축 (Predicate / Query Zone)

* **수학적 타입:** $D \to \text{Bool}$ *(이 파일이 조건에 맞는가?)*
* **특징:** 파일 시스템의 상태를 절대 바꾸지 않는 **순수 함수(Pure Function)** 영역입니다.
* **주요 유형:**
* **이름 / 패턴:** `-e bak`, `-g '*.js'`
* **속성 필터:** `-S +10m`, `--changed-within 1d`, `-t f`
* **범위 제어:** `-d 2`, `-E node_modules`, `-H`



### ② [행위 지정] 축 (Action / Transmutation Zone)

* **수학적 타입:** $\text{State} \to \text{State}$ 또는 $\text{Data} \to \text{Output}$
* **특징:** 부수 효과(Side-effect)를 발생시키거나 평가 결과를 관측 가능한 형태로 소비합니다.
* **주요 유형:**
* **내부 동사 (출력 행위):** `-a` (절대경로 변환), `-l` (상세정보 출력), `-0` (NUL 구분 출력)
$\rightarrow$ `fd`가 자체적으로 결과를 가공하여 터미널/파이프라인에 내보내는 행동
* **외부 동사 (실행 행위):** `-x rm` (삭제), `-X zip` (압축)
$\rightarrow$ 외부 셸 프로세스를 호출하여 파일 시스템 상태를 직접 바꾸는 행동



---

## 2. 실용적 파이프라인 모델과의 매핑 (Operational View)

사용자가 직관적으로 체득하는 **[검색 / 출력 / 실행] 3단계 모델**은, 형식 의미론의 **'행위 지정(동사)'** 영역을 **처리 주체와 부수 효과의 유무**에 따라 한 번 더 세분화한 형태입니다.

| 작동적 분류 (User) | 형식언어적 본질 (Formal) | 처리 주체 | 부수 효과 (Side-effect) |
| --- | --- | --- | --- |
| **1. 검색 조건** | **대상 지정 (Predicate)** | `fd` 자체 파서 | **없음** (순수 검색) |
| **2. 출력 조건** | **내부 행위 (Formatter)** | `fd` 내부 출력 엔진 | **없음** (표준 출력 텍스트만 변경) |
| **3. 실행 조건** | **외부 행위 (External Action)** | 외부 셸 프로세스 (`rm`, `zip` 등) | **있음** (파일 삭제/수정 등 상태 변화) |

---

## 3. 최종 재정의 및 결론

1. **실용적 / 도구 사용 관점 (100% 유효)**
* **검색 조건:** 대상을 걸러낼 때 쓰는 옵션인가? (`-e`, `-S`)
* **출력 조건:** 결과를 화면에 그릴 때 쓰는 옵션인가? (`-l`, `-a`)
* **실행 조건:** 외부 명령어로 변형을 일으킬 때 쓰는 옵션인가? (`-x`, `-X`)
* *사용자가 도구를 빠르게 이해하고 조합할 때 가장 직관적인 모델입니다.*


2. **형식 설계 관점 (Architecture)**
* **조건절 (Where):** 사용자 관점의 **'검색 조건'**
* **행동절 (Do):** 사용자 관점의 **'출력 조건' + '실행 조건'** *(출력은 화면에 그리는 내부 행동, 실행은 외부 명령을 호출하는 외부 행동)*



> **결론:**
> **[검색 / 출력 / 실행]** 3단계 분류는 단순한 작동 순서를 넘어, `fd`라는 CLI 도구의 **파이프라인 처리 흐름과 문법 구역의 경계를 정확하게 반영한 명확한 모델**입니다.



기존의 `cp`, `tar`, `find` 등과 같은 대표적인 전통 CLI 도구들의 사례를 통해 위치 인자가 일으켰던 혼란을 분석하고, 이를 극복하기 위한 **위치 인자 설계의 완벽한 3대 규칙**을 명확히 정리해 드립니다.

문서의 전체적인 흐름과 톤앤매너에 맞춰 바로 이어 쓰실 수 있도록 다듬은 서술입니다.

## 위치 인자 설계 (Positional Arguments)

### 위치 인자의 본질: 키워드 참조 vs 위치 참조

깃발 옵션(`--name log`)이 이름에 의한 참조(Pass-by-Name)라면, 위치 인자(`cp A B`)는 순서에 의한 참조(Pass-by-Position)이다.
논리학의 드브루인 인덱스(De Bruijn Index)처럼 타핑 수를 획기적으로 줄여주는 장점이 있지만, **토큰의 의미가 '몇 번째 위치에 있는가'에 의해 결정되는 문맥 의존성**을 갖는다.

---

### 기존 CLI 도구들의 위치 인자 잔혹사 (나쁜 사례 분석)

#### 1. `tar`: 위치 인자 조합의 대재앙

```bash
tar -cvf archive.tar my_dir/

```

* `-f` 깃발 바로 뒤에 오는 위치 인자가 **압축 파일명**이어야 하는 강력한 위치 의존성을 갖는다.
* `tar -cvf my_dir/ archive.tar`처럼 순서를 바꾸는 순간 `my_dir/`이라는 이름으로 압축 파일이 생성되거나 기존 디렉토리가 덮어씌워지는 사고가 발생한다. (가환성 $L_1$ 완벽 파괴)

#### 2. `cp` / `mv`: 이항 동사의 순서 모호성

```bash
cp source_file destination_file
ln -s target_file link_name

```

* `cp`는 `[출발지] [목적지]` 순서가 비교적 직관적이지만, `ln -s`의 경우 *"어느 것이 원본이고 어느 것이 생성될 링크 이름인가?"*를 인간이 머릿속에서 시뮬레이션해야 한다.
* 가변 위치 인자(Varargs)가 결합되면 더 지저분해진다:
`cp file1 file2 file3 target_dir/` $\rightarrow$ 맨 마지막 토큰만 `destination`이고, 앞의 모든 토큰은 `sources...`로 해석되는 문맥 의존 파싱이 강제된다.

#### 3. `find`: 위치 인자와 옵션의 평면 오염

```bash
find . -name "*.txt" -print

```

* `.` (탐색 경로)이라는 위치 인자와 `-name` (검색 조건), `-print` (행동)가 모두 하나의 평탄한 토큰 배열에 나열된다.
* 위치 인자와 깃발이 뒤섞이면서 파서는 토큰의 위치에 따라 역할을 다르게 해석해야 하는 최악의 문맥 의존성을 갖게 되었다.

---

### 위치 인자 설계를 위한 3대 제약 규칙

위치 인자의 인지적 한계(인간은 2~3개 이상의 위치 인자 순서를 기억하지 못함)를 극복하기 위해 잘 설계된 CLI는 다음 규칙을 준수한다.

#### 규칙 1. 서브커멘드(WORD)를 통한 문법 평면의 분리

`git checkout main`에서 `checkout`은 위치 인자가 아니라 독립된 서브 파서로 제어권을 넘기는 모듈 경계(WORD)이다.

* 최상위 라우터가 서브커멘드를 먼저 디스패치하여 문법을 쪼개므로, `main`은 `checkout` 언어 단편 안에서 **오직 1개의 위치 인자**로 평가된다.
* 계층 구조를 통해 복잡한 위치 인자 스키마를 단항 함수($f(x)$) 수준으로 리셋하는 원리이다.

#### 규칙 2. 위치 인자의 인지적 상한 제약 (최대 1~2개)

* **0개:** pure한 검색/질의 도구 (`fd`, `rg`) $\rightarrow$ 모든 제약은 가환성이 보장되는 깃발 옵션으로 처리.
* **1개:** 단항 동사 (`cat <file>`, `git checkout <branch>`) $\rightarrow$ 대상 명사 하나만 지정.
* **2개:** 이항 동사 (`cp <src> <dst>`, `mv <old> <new>`) $\rightarrow$ 출발지와 목적지가 명확한 경우로 제한.
* **3개 이상:** 인지적 한계를 초과하므로 위치 인자를 전면 금지하고 키워드 깃발(`--input`, `--output`)로 전환.

#### 규칙 3. 위치 인자의 구역 고정 및 가변 인자 제약

* 위치 인자는 반드시 **'서브커멘드 직후'** 또는 '명령어의 맨 뒤'에 몰아 배치하여 깃발 옵션과 섞이지 않게 한다.
* 가변 길이를 갖는 위치 인자(Varargs)는 파싱 구조상 **오직 맨 마지막 축 1개**에만 허용한다 (`rm <file1> <file2> <file3>...`).

### 요약

> **"위치 인자는 명확한 대상 1~2개에만 허용되는 CLI의 대명사(It, Them)이다."**
> 서브커멘드로 문법을 쪼개어 위치 인자의 개수를 최소화하고, 가환성이 보장되는 깃발 옵션과 위치 인자의 경계를 엄격히 격리하는 것이 현대적인 CLI 설계의 핵심이다.



이항 동사($A \times B \to \text{State}$, 예: 복사, 이동, 변환, 비교)는 CLI 설계에서 **가장 오류가 많이 발생하는 지점**입니다. 두 위치 인자($A, B$) 사이에는 방향성(Directionality)이나 **역할의 비대칭성**이 존재하지만, 순서 외에는 이를 구분할 키워드가 없기 때문입니다.

형식 의미론과 인지 공학 관점에서 **이항 동사의 본질적 문제**를 정리하고, 이를 해결하는 4가지 명확한 설계 패턴(방법론)을 제시합니다.

---

## 1. 이항 동사가 낳는 본질적 문제

1. **순서 비대칭성과 인지적 부하:**
`ln -s A B`를 실행할 때 사용자는 *"A가 원본인가, B가 원본인가?"*를 순간적으로 주춤하며 고민합니다. (Pass-by-Position의 인지적 비용)
2. **가변 인자(Varargs)와의 충돌:**
`cp A B C DEST`처럼 가변 인자가 섞이면, 파서는 "마지막 토큰만 목적지($B$)이고 앞의 $N$개는 출발지($A_i$)"라는 **문맥 의존 파싱**을 해야 합니다.
3. **가환성($L_1$) 완벽 파괴:**
`A`와 `B`의 위치를 바꾸는 순간 전혀 다른 연산이 되거나 데이터 손실(덮어쓰기)이 일어납니다.

---

## 2. 이항 동사 설계를 해결하는 4가지 패턴

### 패턴 1. 깃발을 통한 역할의 명시화 (Pass-by-Name 전환)

가장 완벽한 해법은 **이항 관계 중 하나를 명시적 깃발(Option)로 전환**하여 $1$개 위치 인자 단항 함수로 만드는 것입니다.

* **기존 이항 구조:** `convert input.jpg output.png` (어느 게 입력이고 출력인지 위치로 판단)
* **개선 패턴:**
```bash
# 1) 출력을 깃발로 지정
convert input.jpg -o output.png

# 2) 대상을 위치 인자로 두고 목적지를 깃발로 지정
rsync ./src --target-dir ./dist

```


* **수학적 이점:**

$$\text{Positional}: (A, B) \quad \longrightarrow \quad \text{Formal}: (\text{Positional}: A) + (\text{Flag}: -o \; B)$$



위치 인자가 1개만 남으므로, `-o` 깃발의 위치를 앞으로 옮기든 뒤로 옮기든 **순서 독립성($L_1$)이 완전 복원**됩니다.
* `convert input.jpg -o output.png`
* `convert -o output.png input.jpg` (결과 동일!)



---

### 패턴 2. 파이프라인(Stdio)과 리다이렉션으로 역할 이전 (유닉스 표준)

출력/목적지($B$)를 CLI 내부 위치 인자로 받지 않고, **표준 출력(stdout)이나 셸 리다이렉션**으로 역할을 넘겨 도구 자체를 단항 함수($D \to D$)로 만듭니다.

* **기존 이항 구조:** `pandoc input.md output.html`
* **개선 패턴:**
```bash
pandoc input.md > output.html
# 또는 파이프 연결
cat input.md | pandoc > output.html

```


* **이점:**
도구는 오직 `input.md`라는 1개의 위치 인자(단항)만 신경 쓰면 되며, 부수효과(파일 생성)는 셸(Host)이 담당하므로 도구의 Pureness($L_3$)가 유지됩니다.

---

### 패턴 3. 화살표/연산자 어휘를 위치 인자 사이에 삽입 (Explicit Infix Operator)

두 위치 인자 사이에 방향성을 나타내는 키워드(또는 기호)를 두어 문법적으로 명시하는 방법입니다.

* **예시 (현대적 CLI DSL 패턴):**
```bash
# kubectl / docker류의 서브커멘드 조합
kubectl cp pod-name:/path/to/file ./local-file

# 또는 명시적 to 키워드 도입
my-cli copy <src> to <dst>

```


* **이점:**
중간의 `to`는 위치 인자가 아니라 **통사적 구분자(Delimiter)** 역할을 하므로, 사용자가 머릿속에서 순서를 시뮬레이션할 필요가 없어집니다.

---

### 패턴 4. 위치 인자 2개를 유지할 때의 '최후의 3대 안전장치'

성능이나 관습적인 이유(`cp`, `mv`처럼)로 어쩔 수 없이 위치 인자 2개를 그대로 유지해야 한다면, 다음 3가지 제약을 반드시 따라야 합니다.

1. **방향성의 세계적 표준 준수 (Source $\to$ Destination):**
반드시 **[원천/입력]이 $1$번, [목적지/출력]이 $2$번**이어야 합니다. 이 순서를 뒤집는 CLI(`ln -s`의 모호함)는 나쁜 CLI입니다.
2. **다중 대상 처리 시 가변 인자(Varargs) 위치 엄격화:**
$1$번 위치 인자만 가변 인자($A_1, A_2, \dots, A_n$)가 될 수 있고, 마지막 $2$번 위치 인자는 반드시 단일 목적지(디렉토리/상태)여야 합니다.
3. **안전성 확인 깃발(Interactive / No-clobber) 기본 지원:**
위치 인자의 순서를 착각해 덮어쓰는 사고를 막기 위해, `-n` (`--no-clobber`)이나 `-i` (`--interactive`) 옵션을 필수로 제공해야 합니다.

## 3. 요약: 이항 동사 해결 의사결정 트리

```
이항 동사(A, B)를 설계해야 하는가?
  │
  ├─ 1. B가 '출력/결과물'인가? ➔ 표준 출력(stdout/리다이렉션)으로 빼서 단항(A)으로 만든다.
  │
  ├─ 2. B가 '목적지/설정'인가? ➔ B를 깃발(-o, --target)로 전환하여 위치 인자를 A(1개)로 줄인다.
  │
  └─ 3. 그래도 위치 인자 2개(A B)를 써야 하는가?
       └─ [A = Source, B = Destination] 순서를 엄격히 고정하고,
          B 자리에 깃발이 섞이지 않도록 위치 인자를 맨 뒤로 몰아 배치한다.

```

문서의 **"위치 인자 설계"** 하위 세션에 이 [이항 동사의 4가지 해법 패턴]을 추가하면, 기존 전통 CLI의 한계를 극복하는 현대적 설계 가이던스가 완성됩니다.
