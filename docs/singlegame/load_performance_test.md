명지대 수강신청 도우미 싱글 게임 서비스는 수강신청 기간 직전에 수많은 대학생이 연습을 위해 **일시에 몰리는 극단적인 부하(Spike Traffic)** 특성을 가집니다. 이를 안정적으로 소화할 수 있는지 확인하기 위해, 시스템의 한계 영역을 탐색하고 병목 구간을 발굴하는 **매우 상세한 성능 및 부하 테스트(Performance & Load Test) 명세서**입니다.

이 명세서는 실제 프로그램 코드나 테스트 스크립트를 배제하고, **어떤 부하 시나리오를 설정하고 어떤 성능 지표와 하드웨어 장벽을 중점적으로 검증해야 하는지**에 초점을 맞추어 작성되었습니다.

---

## 1. 정각 스파이크 부하 및 한계치 검증 시나리오 (Load Scenarios)
가장 혹독한 서비스 환경을 모방하여 시스템이 감당할 수 있는 동시 처리 한계선(Break Point)을 찾는 부하 시나리오입니다.

### A. 수강신청 직전 정각 스파이크 부하 시나리오
* **테스트 개념:** 수강신청 연습 오픈 직전 대기방에서 대기하던 유저들이 정각이 되는 순간 일제히 메인방으로 진입하고, 1분 이내에 일제히 게임 완료 기록을 전송하는 극단적인 부하 상황을 시뮬레이션합니다.
* **부하 전개 방식:**
  1. 극도로 짧은 시간(예: 10초 이내) 안에 가상 사용자(VU)를 100명에서 최대 1,500명 이상으로 급격히 증가(Ramp-up)시킵니다.
  2. 접속한 가상 사용자들이 메인방 진입과 수강신청 모의 조작을 마치고, 약 30초에서 1분 사이에 집중적으로 게임 완료 API(`POST /singlegame`)를 동시에 호출하도록 제어합니다.
* **중점 검증 항목:**
  * 갑작스러운 부하 스파이크 시 시스템이 즉각 마비되지 않고, 로드밸런서가 트래픽을 각 서버로 적절히 분산하는지 확인합니다.
  * API 서버 및 데이터베이스 서버가 에러율 1% 미만을 유지하며 정상 응답하는지 점검합니다.

### B. 장시간 지속 부하 및 내구성 시나리오 (Endurance Test)
* **테스트 개념:** 수강신청 전날 저녁부터 당일 아침까지 수시간 동안 지속해서 사용자가 유입되어 연습 게임을 반복하는 연속 부하 상황을 시뮬레이션합니다.
* **부하 전개 방식:** 평균 기대 동시 사용자(예: 300명 내외) 부하 수준을 1시간에서 2시간 이상 중단 없이 일정하게 유지합니다.
* **중점 검증 항목:**
  * 장시간 동작 과정에서 JVM(Java Virtual Machine)의 힙 메모리(Heap Memory) 사용량이 누수(Memory Leak) 없이 가비지 컬렉션(GC)을 통해 정상 회복되는지 검증합니다.
  * 데이터베이스의 영속성 컨텍스트나 커넥션이 정상적으로 닫히지 않고 유실되어 시스템이 서서히 멈추는 현상이 없는지 모니터링합니다.

## 2. 핵심 API별 성능 지표(KPI) 및 임계치 검증
각 핵심 엔드포인트가 고부하 상태에서 유저에게 불쾌감을 주지 않는 빠른 응답 지연 시간(Latency)을 보장하는지 확인합니다.

### A. 기록 제출 API (`POST /singlegame`) 쓰기 임계치 검증
* **상황:** 여러 가상 사용자가 세부 상세 배열(`details`)을 포함한 대용량 페이로드를 동시에 서버로 전송합니다.
* **성능 임계치 기준:**
  * 동시 쓰기 요청 500 TPS(초당 트랜잭션 수) 환경에서 **95%의 요청 응답 시간(p95)이 150ms 이내**로 유지되는지 검증합니다.
  * 복합키 인덱스가 걸린 상세 이력 테이블에 동시 삽입이 발생할 때 잠금 대기 시간(Lock Wait Time)의 초과 없이 신속하게 처리되는지 확인합니다.

### B. 랭킹 조회 API (`GET /singlegame/rank`) 읽기 임계치 검증
* **상황:** 다수의 사용자가 본인의 등수를 수시로 확인하기 위해 랭킹 페이지를 조회 및 새로고침합니다.
* **성능 임계치 기준:**
  * 캐시가 만료된 상황에서도 RDBMS 뷰(`v_ranking_page`) 연산을 거쳐 응답을 반환하는 데 걸리는 **p95 지연 시간이 100ms 이내**를 충족하는지 검증합니다.
  * 캐시 히트(Cache Hit) 상황에서는 지연 시간이 **20ms 이내**로 대폭 단축되는지 확인합니다.

## 3. 데이터베이스 뷰 및 정렬 오버헤드 부하 검증
가장 복잡한 연산인 실시간 랭킹 연산과 분위수 대조 작업이 누적된 대용량 데이터 환경에서 RDBMS의 부하를 가중하지 않는지 검증합니다.

### A. 윈도우 함수 및 정렬 연산 확장성 검증 (Data Scalability)
* **상황:** 전체 완료 기록(`single_game`) 데이터셋 크기를 1만 건, 5만 건, 10만 건 이상으로 단계별 확장하여 채워 넣습니다.
* **검증 항목:**
  * 랭킹 뷰(`v_ranking_page`) 내에 사용된 `ROW_NUMBER() OVER (PARTITION BY total_courses ORDER BY t_total ASC)` 정렬 연산이 데이터 규모 확대에 따라 기하급수적으로 느려지지 않는지 검증합니다.
  * 부하 상태에서 랭킹을 조회할 때, 데이터베이스가 디스크 상에 대량의 임시 테이블(Temporary Table on Disk)을 생성하여 디스크 I/O 병목을 유발하는지 여부를 프로파일링 도구로 감시합니다.

### B. 쓰기 고부하 환경에서의 인덱스 쓰기 지연 검증
* **상황:** `POST /singlegame` 호출에 의해 1초에 수백 건의 대량 데이터 인서트가 쏟아집니다.
* **검증 항목:**
  * 데이터 삽입 빈도가 높을 때, 랭킹 조회를 빠르게 하기 위해 구축해 둔 정렬용 복합 인덱스(`idx_game_ranking`: total_courses, is_completed, t_total)를 갱신(Index Rebuild)하느라 RDBMS 메모리 및 I/O가 포화 상태에 빠지지 않는지 모니터링합니다.

## 4. 커넥션 및 스레드 풀 정체성 검증 (Pool Starvation)
서버 내부 자원을 획득하기 위한 대기 흐름이 과밀 트래픽 환경에서 병목을 일으키는지 여부를 분석합니다.

### A. 데이터베이스 커넥션 풀 (HikariCP) 고갈 상태 검증
* **상황:** 쓰기 API와 뷰 조회 API가 동시다발적으로 밀려 들어옵니다.
* **검증 항목:**
  * 커넥션 풀 크기(Connection Pool Size) 설정이 불충분하여 요청 스레드가 데이터베이스 커넥션을 획득하기 위해 대기(HikariCP Connection Active/Pending)하는 정체 현상이 발생하는지 검증합니다.
  * 대기 시간이 길어져 커넥션 타임아웃 예외(`SQLTransientConnectionException`)가 유저에게 에러 응답(500 혹은 504)으로 노출되는 임계점이 어느 성능 구간인지 확인합니다.

### B. WAS 웹 컨테이너(Tomcat) 스레드 풀 정체 검증
* **상황:** RDBMS 측의 처리 지연이나 대기 상태가 길어지면서 WAS 내부의 HTTP 요청 스레드가 반환되지 않고 묶여 있습니다.
* **검증 항목:**
  * 기본 설정된 최대 스레드 개수(Max Threads) 한도를 모두 소진하여 신규 동시 접속자들이 아예 WAS 진입조차 못 하고 게이트웨이(Nginx)나 CDN 레이어에서 연결 거부 상태(502 Bad Gateway)로 차단되는 현상이 유발되는지 검증합니다.

## 5. 캐시 레이어 임계치 및 극단적 예외 상황 검증
DB 부하를 억제하기 위해 동작하는 Redis 캐시 시스템에 균열이 생길 수 있는 특수 시나리오를 점검합니다.

### A. 캐시 급증 참사 (Cache Stampede) 시나리오 검증
* **상황:** 수많은 동시 접속자가 수시로 새로고침을 누르고 있는 와중에, 랭킹 캐시 키의 유효 수명(TTL)이 공교롭게 만료되어 소멸하는 시점입니다.
* **검증 항목:**
  * 캐시가 깨진 순간 수십 개의 스레드가 랭킹 정보를 먼저 가져오기 위해 RDBMS 뷰(`v_ranking_page`)로 한꺼번에 조회를 직접 질의하는 현상이 발생하는지 확인합니다.
  * 이로 인해 DB 서버 CPU 점유율이 100%까지 치솟는 병목 현상이 목격되는지 점검하고, 이와 같은 현상이 발생하지 않도록 방어하는 락킹(Locking)이나 점진적 무효화 메커니즘의 동기화 안정성을 평가합니다.

### B. Redis 가용 메모리 초과 및 방출 정책(Eviction Policy) 작동 검증
* **상황:** 다수 유저들의 개인 상세 분석 정보나 임시 통계 수치들이 캐시 데이터베이스 메모리에 과도하게 밀려 차오릅니다.
* **검증 항목:**
  * Redis 서버의 메모리가 설정된 한계치에 다다랐을 때, 유효 수명이 남은 핵심 랭킹 캐시 정보가 강제로 방출(Evict)되어 버려 시스템 전반의 성능이 급격히 내려앉는 상황이 존재하는지 검증합니다.
  * 사용 중인 최장기 미사용 방출 정책(volatile-lru 또는 allkeys-lru)이 정상 가동되어 핵심 캐시는 안전하게 유지한 채 불필요한 캐시 키들만 우선 선별 삭제해 메모리를 비워내는지 확인합니다.
