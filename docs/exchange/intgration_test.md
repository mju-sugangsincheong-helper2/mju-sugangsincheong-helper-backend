수강신청 과목 교환 매칭 시스템의 **통합 테스트(Integration Test)** 시나리오를 안내해 드립니다. 

통합 테스트는 개별 컴포넌트(API 컨트롤러, 비즈니스 서비스, DB 파티션, Redis 캐시, 비동기 이벤트 채널)들이 서로 유기적으로 맞물려 데이터의 일관성을 유지하는지 검증하는 것이 목적입니다. 

---

### I. 비즈니스 시나리오 (End-to-End) 통합 테스트

실제 서비스에서 유저들이 상호작용하는 흐름을 그대로 모사하여 전체 컴포넌트의 유기적 흐름을 검증합니다.

#### 1. 3자 간 순환 매칭 성공 및 방 생성 흐름
*   **시나리오 목표:** 사용자들이 순차적으로 의사를 등록할 때, 마지막 등록자가 사이클을 완성하며 비동기로 방이 생성되고, 관련자들의 화면 폴링 데이터가 일관되게 업데이트되는지 검증합니다.
*   **테스트 절차:**
    1. **준비 단계:** 대기자 A(`101 -> 102` 등록)와 대기자 B(`102 -> 103` 등록)가 존재하는 상태를 DB에 구성합니다.
    2. **행위 단계:** 대기자 C가 API(`POST /api/v1/exchange/intents`)를 통해 `103 -> 101` 의사를 등록합니다.
    3. **검증 단계 (Assert):**
        *   C의 등록 요청이 정상 응답(200 OK)을 반환하는지 확인합니다.
        *   비동기 이벤트 채널을 거쳐 탐색 로직이 트리거되고, `EXCHANGE_ROOM`에 A, B, C를 묶는 고유 `cycle_hash` 방 레코드가 자동 생성되는지 확인합니다.
        *   `EXCHANGE_ROOM_INTENT` 테이블에 3명의 매핑 데이터가 생성되는지 확인합니다.
        *   Redis 캐시 내 `exchange::{term}:feed:cache`에 C의 정보가 추가되고, A, B, C 전원의 `rooms:cache`가 제거(Evict)되었는지 확인합니다.
        *   A, B, C가 메인 화면 폴링 API(`GET /api/v1/exchange/main`)를 호출했을 때, 캐시 미스가 발생하며 DB에서 신규 방 정보를 가공해 캐시를 정상 재적재하고, 새로 생성된 방 목록을 정상 응답하는지 검증합니다.

#### 2. 대화방 내 메시지 전송 및 실시간 폴링 동기화 흐름
*   **시나리오 목표:** 매칭된 방 안에서 대화가 오갈 때, 발신자와 수신자의 메시지 데이터 및 안 읽은 메시지 수(배지)가 오차 없이 실시간으로 표기되는지 검증합니다.
*   **테스트 절차:**
    1. **준비 단계:** A, B, C가 참여 중인 활성 대화방이 존재하며, 이전 대화는 모두 읽음 상태로 정렬되어 있습니다.
    2. **행위 단계 1:** A가 대화방에서 메시지 전송 API(`POST /api/v1/exchange/rooms/{roomId}/messages`)를 호출합니다.
    3. **검증 단계 1 (Assert):**
        *   A의 전송 API 응답이 성공하며, `EXCHANGE_ROOM_MESSAGE`에 정상 기록되는지 확인합니다.
        *   A의 `EXCHANGE_ROOM_READ_STATUS` 내 `last_read_message_id`가 방금 보낸 메시지 ID로 즉시 동기화되는지 확인합니다.
        *   Redis 내 이 방에 참여한 멤버(A, B, C) 전원의 `rooms:cache`가 제거(Evict)되는지 확인합니다.
    4. **행위 단계 2:** 수신자 B와 C가 메인 화면 폴링 API(`GET /api/v1/exchange/main`)를 주기적으로 호출하는 상황을 모사합니다.
    5. **검증 단계 2 (Assert):**
        *   B와 C의 폴링 결과로 가공된 JSON 데이터 내 `unreadCount`가 1로 증가하고, `lastMessageContent`에 A가 보낸 메시지가 보이나, A 본인의 폴링 데이터에서는 `unreadCount`가 0으로 나오는지 검증합니다.
    6. **행위 단계 3:** B가 대화방에 진입하여 메시지 이력 조회 API(`GET /api/v1/exchange/rooms/{roomId}/messages`)를 호출합니다.
    7. **검증 단계 3 (Assert):**
        *   B의 `EXCHANGE_ROOM_READ_STATUS` 상 포인터가 A의 메시지 ID로 최신화됩니다.
        *   B가 다시 메인 화면을 폴링했을 때 `unreadCount`가 0으로 복구되며, 같은 시각 채팅방에 진입하지 않은 C의 `unreadCount`는 여전히 1을 유지하는지 검증합니다.

#### 3. 의사 철회 및 대화방 순차 비활성화 흐름
*   **시나리오 목표:** 사용자가 등록한 카드를 삭제할 때, 해당 카드와 얽혀 있던 대화방들이 규정된 비즈니스 규칙($N, D$)에 맞춰 순차적으로 비활성화되거나 이탈 안내가 이루어지는지 검증합니다.
*   **테스트 절차:**
    1. **준비 단계:** 2인 방 하나와 3인 방 하나에 동시에 참여하고 있는 유저 A의 데이터를 준비합니다.
    2. **행위 단계:** A가 자신의 교환 의사 철회 API(`DELETE /api/v1/exchange/intents/{intentId}`)를 호출합니다.
    3. **검증 단계 (Assert):**
        *   A의 의사 정보가 `is_deleted = TRUE`로 마킹되는지 확인합니다.
        *   **2인 방의 변화:** 잔여 활성 참여자가 1명이 되므로 방의 전체 상태가 `ALL_DELETE`로 변하고 `EXCHANGE_ROOM.is_active = FALSE`로 전환되며 시스템 이탈 메시지가 정상 적재되는지 확인합니다.
        *   **3인 방의 변화:** 잔여 활성 참여자가 2명이 되므로 방의 전체 상태가 `PARTIAL_DELETE`로 전환되고 활성 상태(`is_active = TRUE`)는 유지되는지 확인합니다.
        *   A 및 영향받은 모든 방 참여자들의 Redis 캐시(`intents:cache`, `rooms:cache`)가 정상 무효화되는지 확인합니다.

### II. 인프라 및 DB 파티셔닝 통합 테스트

실제 데이터베이스 분할 정책과 네트워크 레이어에서 발생할 수 있는 데이터 격리 및 정합성을 검증합니다.

#### 1. 학기(Term) 분리에 따른 데이터 격리 테스트
*   **시나리오 목표:** PostgreSQL의 `PARTITION BY LIST (term)` 설계가 실제 애플리케이션 서비스 단에서 혼선 없이 바인딩되고 격리되는지 검증합니다.
*   **테스트 절차:**
    1. **행위 단계:** `term = '202610'`(26년 1학기) 파티션에 과목 매칭 데이터(`10023 -> 40101`)를 적재하고, 동일 시점에 `term = '202620'`(26년 2학기) 파티션에도 동일한 사용자의 동일 과목 요청 데이터를 적재합니다.
    2. **검증 단계 (Assert):**
        *   물리 테이블인 `exchange_intent_202610`과 `exchange_intent_202620` 각각에 데이터가 할당되어 적재되었는지 SQL로 직접 검증합니다.
        *   '202610' 학기 정보로 구동된 탐색기가 '202620' 테이블의 데이터를 조회하거나 섞어 쓰지 않는지, 쿼리 수행 시 반드시 파티션 키(`term`) 조건이 바인딩되어 동작하는지 확인합니다.

#### 2. Redis 캐시 파티셔닝(Prefix 격리) 테스트
*   **시나리오 목표:** 학기가 전환되었을 때 캐시 공간에서 동일한 사용자 ID를 갖더라도 학기별 데이터가 독립적으로 적재 및 조회되는지 검증합니다.
*   **테스트 절차:**
    1. **행위 단계:** 동일한 사용자(`member_id = 9931`)에 대해 `term = '202610'` 기준의 방 목록과 `term = '202620'` 기준의 방 목록을 각각 셋업합니다.
    2. **검증 단계 (Assert):**
        *   Redis 내에 `exchange::202610:member:9931:rooms:cache`와 `exchange::202620:member:9931:rooms:cache` 두 개의 개별 키로 데이터가 충돌 없이 적재되는지 확인합니다.
        *   한 학기의 캐시를 Evict 하였을 때, 다른 학기의 캐시 데이터가 유실되지 않고 원형을 유지하는지 검증합니다.

### III. 예외 복구 및 동시성 통합 테스트

시스템 장애 상황이나 여러 사용자가 동시에 동일 대상을 조작할 때 발생할 수 있는 극단적인 시나리오를 검증합니다.

#### 1. 트랜잭션 롤백 시 DB-Redis 정합성 테스트
*   **시나리오 목표:** 데이터베이스 트랜잭션 수행 도중 알 수 없는 에러로 롤백이 진행되었을 때, Redis 캐시 갱신/무효화 로직이 실행되어 데이터 불일치가 일어나는 현상을 방지하는지 확인합니다.
*   **테스트 절차:**
    1. **준비 단계:** 의사 등록 비즈니스 로직 도중, DB Insert는 성공하나 트랜잭션이 커밋되기 전 강제로 예외(Exception)를 일으킵니다.
    2. **행위 단계:** 등록 API 호출을 수행합니다.
    3. **검증 단계 (Assert):**
        *   DB 상에 데이터가 롤백되어 존재하지 않음을 확인합니다.
        *   트랜잭션 커밋 완료 후에만 캐시를 제어하도록 구성된 이벤트 리스너(예: TransactionalEventListener 등)가 작동하여 Redis에 어떠한 후처리(LPUSH, Evict 등)도 유발하지 않았음을 검증합니다.

#### 2. 다중 스레드 하의 동일 사이클 방 생성 충돌 테스트 (Concurrency)
*   **시나리오 목표:** 두 사용자가 서로 교환이 가능한 카드를 등록하여, 양방향 스레드에서 동시에 동일한 `cycle_hash`를 탐색하고 방 생성을 수행하려 경쟁할 때 데드락이나 중복 방이 생기지 않는지 확인합니다.
*   **테스트 절차:**
    1. **준비 단계:** 다중 스레드 환경에서 거의 동일한 밀리초 단위로 동일한 사이클에 연루된 두 사용자의 방 생성 비즈니스 메서드를 호출합니다.
    2. **행위 단계:** 인위적으로 쓰레드 경쟁을 유발합니다.
    3. **검증 단계 (Assert):**
        *   두 요청 중 하나는 성공하고 다른 하나는 DB의 `UNIQUE` 제약조건과 `ON CONFLICT DO NOTHING` 처리에 의해 예외 없이 무사히 트랜잭션이 마무리되는지 확인합니다.
        *   `EXCHANGE_ROOM`에 생성된 방이 오직 단 1개만 존재하는지 확인합니다.

#### 3. Redis 캐시 전체 유실(Cold Start) 시 자동 복구 테스트
*   **시나리오 목표:** Redis 서버가 재부팅되어 모든 캐시가 유실된 상황(Cache Miss 100%)에서, 유저들의 대규모 유입 시 서비스가 중단 없이 DB를 기반으로 캐시를 조용히 복구해 내는지 검증합니다.
*   **테스트 절차:**
    1. **준비 단계:** DB에 기존 매칭 내역 및 방 정보를 대량 적재한 상태에서 Redis 데이터를 강제로 모두 초기화합니다 (`FLUSHALL`).
    2. **행위 단계:** 메인 화면 폴링 API(`GET /api/v1/exchange/main`)를 호출합니다.
    3. **검증 단계 (Assert):**
        *   API가 타임아웃이나 예외 없이 정상 응답(200 OK)을 반환하는지 확인합니다.
        *   로그를 통해 복잡한 집계 조인 쿼리가 DB에서 실행되었음을 확인하고, 호출 직후 Redis 내에 유실되었던 `feed:cache`, `intents:cache`, `rooms:cache` 3종 세트가 올바른 구조로 재적재되었는지 검증합니다.
        *   캐시 적재 이후 동일 API 재호출 시 DB 쿼리가 발생하지 않고 Redis에서 응답이 나가는지 검증합니다.
