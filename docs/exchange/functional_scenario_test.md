과목 교환 매칭 시스템의 요구사항과 5초 주기 폴링 방식의 화면 구성을 기반으로, QA 및 서비스 검증 관점에서 수행해야 할 **기능 테스트(Functional Test)** 및 **사용자 시나리오 테스트(Scenario Test)** 시나리오를 상세하게 정리해 드립니다.

본 테스트는 코드나 내부 로직이 아닌, **사용자가 화면(UI)에서 겪게 되는 기능적 동작과 서비스 흐름**을 검증하는 데 초점을 맞춥니다.

---

### 1. 주요 기능별 테스트 (Functional Testing)

화면에 구현된 각 개별 기능 요소가 기획 의도대로 올바르게 동작하는지 확인하는 테스트입니다.

#### ① 메인 화면 페이지 및 5초 폴링 동작
*   **검증 목적:** 메인 화면 진입 시 초기 데이터 노출 및 주기적 화면 갱신이 자연스럽게 이루어지는지 확인합니다.
*   **테스트 절차 및 확인 사항:**
    *   **화면 초기 진입:** 메인 페이지 진입 시 '최근 등록된 교환 의사 피드', '내가 등록한 intent 목록', '구성된 방 목록' 영역이 각각 올바른 정보로 채워지는지 확인합니다.
    *   **5초 주기 자동 갱신:** 메인 화면에 대기하는 동안, 사용자가 수동으로 새로고침을 하지 않아도 5초마다 피드가 갱신되거나 방 목록의 정보(안 읽은 메시지 수, 마지막 글)가 동적으로 업데이트되는지 확인합니다.
    *   **비정상 네트워크 대응:** 폴링 도중 인터넷 연결이 일시적으로 끊겼다가 재연결되었을 때, 폴링이 멈추지 않고 재개되는지 확인합니다.

#### ② 신규 Intent 등록 기능
*   **검증 목적:** 사용자가 버릴 과목과 원하는 과목 번호를 입력하여 교환 카드를 등록하는 기능입니다.
*   **테스트 절차 및 확인 사항:**
    *   **정상 입력:** 학수번호와 분반 정보가 포함된 숫자 식별자(예: 버릴 과목 `10023`, 원하는 과목 `40101`)를 입력하고 등록을 누릅니다. 카드 등록 양식이 닫히고 '자신의 등록된 intent 목록'에 해당 카드가 즉시 추가되는지 확인합니다.
    *   **동일 과목 예외 처리:** 버릴 과목과 원하는 과목에 동일한 번호(`10023` -> `10023`)를 입력하고 등록을 시도할 때, UI 상에서 에러 메시지가 표시되며 등록이 차단되는지 확인합니다.
    *   **유효성 검증:** 입력란을 비워두거나 숫자가 아닌 형식의 텍스트를 입력했을 때 적절한 경고 안내가 노출되는지 확인합니다.

#### ③ 최근 교환 의사 피드 및 무한 스크롤
*   **검증 목적:** 실시간으로 올라오는 다른 사용자들의 교환 의사를 확인하고 탐색하는 기능입니다.
*   **테스트 절차 및 확인 사항:**
    *   **실시간 추가 노출:** 다른 사용자가 다른 브라우저에서 카드를 등록하면, 본인의 메인 화면 '최근 등록된 교환 의사 피드' 영역 최상단에 해당 카드가 5초 폴링 주기 내에 나타나는지 확인합니다.
    *   **무한 스크롤 동작:** 피드 영역을 하단으로 스크롤할 때, 끊김 현상 없이 이전 등록된 카드들이 계속 로드되는지 확인합니다.
    *   **취소된 카드 배제:** 철회(삭제)된 카드는 피드 목록이나 무한 스크롤 결과에서 더 이상 노출되지 않는지 확인합니다.

#### ④ 구성된 방 목록 및 ON/OFF 토글
*   **검증 목적:** 매칭이 성사되어 개설된 방들의 상태와 알림 설정을 제어하는 기능입니다.
*   **테스트 절차 및 확인 사항:**
    *   **방 목록 요약 정보:** 목록 내 각 대화방 카드에 '안 읽은 메시지 수(빨간 배지)', '마지막으로 전송된 메시지 내용', '마지막 대화 시간'이 명확히 표시되는지 확인합니다.
    *   **OFF 토글(숨기기) 동작:** 방 목록 우측의 알림/숨김 토글을 'OFF'로 전환합니다. 해당 방이 목록에서 즉시 사라지는지 확인하고, 5초 주기 폴링이 수행되어도 해당 방이 다시 나타나지 않는지 확인합니다.
    *   **ON 토글(복구) 동작:** (설정 페이지 등에서) 토글을 다시 'ON'으로 켜면, 메인 화면의 구성된 방 목록에 기존 안 읽은 메시지 수와 마지막 메시지 정보가 유지된 채 다시 노출되는지 확인합니다.

#### ⑤ 채팅방 페이지 및 대화 기능
*   **검증 목적:** 특정 대화방에 입장하여 실시간 메시지를 주고받는 기능입니다.
*   **테스트 절차 및 확인 사항:**
    *   **방 입장 시 읽음 처리:** 메인 화면에서 안 읽은 메시지가 존재하던 방의 '입장' 버튼을 누릅니다. 대화방에 진입하는 순간 빨간 배지가 사라지며 메인 화면에서도 안 읽은 메시지 수가 0으로 갱신되는지 확인합니다.
    *   **시스템 웰컴 메시지:** 처음 방에 입장했을 때 상단 혹은 첫 메시지로 "매칭이 완료되었습니다. 교환 협의를 시작하세요" 등의 시스템 메시지가 올바르게 렌더링되는지 확인합니다.
    *   **과거 대화 내역 페이징:** 대화방 내부에서 위로 스크롤할 때, 이전 대화 목록이 누락 없이 순차적으로 불러와지는지 확인합니다.

### 2. 대표 서비스 시나리오 테스트 (Scenario Testing)

실제 대학생 사용자가 서비스를 이용할 때 겪는 일련의 여정(User Journey)을 바탕으로 복합적인 상태 흐름을 검증합니다.

#### 시나리오 1: [교환 성공 및 실시간 조율 여정]
> **목적:** 두 사용자의 교환 카드가 매칭되어 대화를 나누고 시간 약속을 잡는 전체적인 사용 흐름을 검증합니다.

1.  **사용자 A**는 메인 화면에서 버릴 과목 `10023`, 원하는 과목 `40101` 카드를 등록합니다.
2.  **사용자 B**는 메인 화면에서 버릴 과목 `40101`, 원하는 과목 `10023` 카드를 등록합니다.
3.  **검증 지표:** 
    *   등록 완료 후, A와 B 모두 5초 이내에 메인 화면 '구성된 방 목록'에 신규 대화방 카드가 생성되는 것을 확인합니다.
4.  **사용자 A**가 대화방에 입장하여 "안녕하세요. 혹시 지금 교환 가능하신가요?"라고 메시지를 보냅니다.
5.  **사용자 B**의 메인 화면에 있는 해당 대화방 카드에 안 읽은 메시지 수 `1` 배지가 노출되는지 확인합니다.
6.  **사용자 B**가 대화방에 입장합니다. 배지가 즉시 사라지며, A가 보낸 메시지를 확인합니다.
7.  **사용자 B**가 "네, 지금 에브리타임 확인하면서 바로 진행해요"라고 답장을 보냅니다.
8.  **결과 확인:** 두 사람 모두 실시간으로 메시지가 누락 없이 송수신되며 대화가 원활히 오가는지 최종 확인합니다.

#### 시나리오 2: [다자간 매칭 중 일부 이탈 여정]
> **목적:** 3자 간 순환 매칭(A -> B -> C -> A)이 성사된 대화방에서 한 명이 변심하여 카드를 철회할 때, 방의 활성 상태 변화와 남은 유저들에게 미치는 알림 효과를 검증합니다.

1.  **사용자 A, B, C**가 각각 매칭 조건을 충족하여 3인 대화방이 생성됩니다.
2.  **사용자 A**가 마음이 바뀌어 본인의 메인 화면 '내가 등록한 intent 목록'에서 해당 카드의 '철회(삭제)' 버튼을 클릭합니다.
3.  **사용자 A 측 화면 검증:** A의 화면에서 등록한 교환 카드가 사라지고, 해당 대화방 역시 목록에서 영구 비활성화 처리되는지 확인합니다.
4.  **사용자 B, C 측 화면 검증:**
    *   대화방 내부에 "A님이 교환 의사를 취소하여 방이 일부 비활성화되었습니다"라는 시스템 안내 메시지가 생성되었는지 확인합니다.
    *   B와 C는 여전히 서로 거래를 조율할 수 있는 상태이므로 대화방 자체는 닫히지 않고 유지되는지 확인합니다. (방의 상태가 UI 상에서 `PARTIAL_DELETE` 등의 경고 라벨로 표시되는지 확인)
5.  이어서 **사용자 B**마저 카드를 철회합니다.
6.  **사용자 C 측 화면 검증:** 이제 잔여 활성 참여자가 1명이 되므로, C의 대화방은 완전히 비활성화(`ALL_DELETE`) 상태로 잠겨 대화 입력을 할 수 없게 되고, 시스템 종료 메시지가 표시되는지 확인합니다.

#### 시나리오 3: [방 숨기기(OFF) 토글 후 상대방 인지 여정]
> **목적:** 한 사용자가 특정 방을 일시적으로 숨김(OFF) 처리했을 때, 상대방에게 이 사실이 투명하게 전달되어 불필요한 대기 오버헤드를 막아주는지 검증합니다.

1.  **사용자 A**와 **사용자 B**가 대화방에서 이야기를 나누던 중, **사용자 A**가 수업에 들어가기 위해 목록에서 해당 대화방의 토글 스위치를 'OFF'로 변경합니다.
2.  **사용자 A 측 화면 검증:** A의 메인 화면 '구성된 방 목록'에서 해당 대화방 카드가 즉시 숨겨져 보이지 않는지 확인합니다.
3.  **사용자 B 측 화면 검증:**
    *   **사용자 B**의 화면 내 해당 대화방에 "상대방이 방을 숨겼거나 알림을 끈 상태입니다"라는 표시(방 상태 `PARTIAL_OFF` UI 적용)가 실시간으로 나타나는지 확인합니다. 이를 통해 B가 "상대방이 지금은 대화에 즉시 반응하기 어렵다"는 사실을 인지할 수 있는지 검증합니다.
4.  수업이 끝난 후 **사용자 A**가 토글 스위치를 다시 'ON'으로 변경합니다.
5.  **사용자 B 측 화면 검증:** B의 화면에서 상대방의 숨김 경고 표시가 사라지고 다시 정상 활성(`ACTIVE`) 상태로 UI가 복구되는지 확인합니다.
