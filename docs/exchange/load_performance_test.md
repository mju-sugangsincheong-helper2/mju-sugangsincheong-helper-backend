수강신청 과목 교환 시스템은 **5초 주기 폴링(Polling)으로 인한 압도적인 읽기(Read) 트래픽**과, **매칭 탐색(Graph Search) 및 캐시 무효화(Eviction)로 인한 순간적인 쓰기(Write) 트래픽**이 공존하는 특성을 가지고 있습니다. 

수강신청 당일 대규모 학생들이 몰리는 상황을 대비하여 진행해야 할 **성능 및 부하 테스트(Performance & Load Testing) 방안**을 구체적으로 정리해 드립니다.

### 1. 핵심 부하 테스트 시나리오 설계

가장 빈번하게 발생하거나 시스템을 중단시킬 위험이 높은 3가지 가상 시나리오를 구성하여 테스트를 진행합니다.

#### 시나리오 ①: 피크타임 "5초 폴링 스톰" 테스트 (Read Heavy)
*   **목적:** 대규모 동시 접속자가 5초마다 메인 화면 및 채팅방 데이터를 요청할 때, 서버와 캐시 레이어가 감당할 수 있는 한계를 검증합니다.
*   **테스트 환경 세팅:**
    *   가상 사용자(Virtual Users, VU)를 수천~수만 명 수준으로 점진적으로 늘려가며 유입시킵니다.
    *   각 가상 사용자는 5초 주기로 `GET /api/v1/exchange/main` 및 `GET /api/v1/exchange/rooms/{id}/messages`를 번갈아 호출합니다.
*   **중점 검증 사항:**
    *   **캐시 히트율(Cache Hit Rate):** 대다수 요청이 Redis 캐시에서 처리되는지 모니터링합니다. (목표: 95% 이상 캐시 히트)
    *   **지연 시간(Latency):** 사용자가 급증하더라도 조회 응답 속도가 SLA(예: 200ms 이내)를 유지하는지 확인합니다.
    *   **네트워크 대역폭:** 서버 및 Redis의 네트워크 입출력(I/O) 대역폭 포화 여부를 확인합니다.

#### 시나리오 ②: 수강신청 오픈 직후 "동시 등록 및 매칭 탐색" 테스트 (Write & CPU Heavy)
*   **목적:** 수강신청이 시작되자마자 수많은 학생이 "버릴 과목/원하는 과목" 카드를 등록할 때, 비동기 그래프 탐색 엔진과 데이터베이스가 감당하는 부하를 검증합니다.
*   **테스트 환경 세팅:**
    *   준비된 가상 사용자들이 초당 수백~수천 건의 속도로 `POST /api/v1/exchange/intents` 등록 API를 밀어 넣습니다.
*   **중점 검증 사항:**
    *   **이벤트 큐 적체 현상:** Intent 등록 시 발생하는 비동기 이벤트(사이클 탐색 트리거)가 메시지 큐(Kafka, RabbitMQ, Spring Event 등)에 쌓여 지연이 발생하지 않는지 확인합니다.
    *   **메모리 내 그래프 탐색 Latency:** 실시간으로 노드(과목)와 간선(의사)이 추가될 때, 그래프 탐색 알고리즘이 점진적으로 느려지지 않고 평균 수 밀리초(ms) 이내에 연산을 마칠 수 있는지 확인합니다.
    *   **방 생성 동시성 처리:** 동시다발적으로 동일한 사이클이 탐색되었을 때, DB 락 대기(Lock Contention)로 인해 커넥션 풀이 마르거나 데드락이 발생하지 않는지 검증합니다.

#### 시나리오 ③: "도미노 캐시 무효화(Eviction) 및 DB 스파이크" 테스트 (Cache & DB Integrity)
*   **목적:** 특정 사용자의 카드 철회나 활발한 채팅 메시지 발송이 주변 사용자들의 캐시를 무효화(Evict)시킬 때, 순간적으로 DB로 몰리는 조회 트래픽(Cache Stampede) 현상을 견디는지 검증합니다.
*   **테스트 환경 세팅:**
    *   대다수 사용자가 5초 폴링을 수행하는 상황(CACHE 3 사용 중)에서, 일부 사용자들이 연쇄적으로 메시지를 전송하거나 카드를 취소(Evict 유발)하도록 유도합니다.
*   **중점 검증 사항:**
    *   **DB CPU 및 커넥션 스파이크:** 캐시가 비워진 유저들이 다음 5초 폴링 때 동시에 DB 복구용 조인(Join) 쿼리를 날릴 때, DB CPU 사용량이 80% 이상으로 치솟거나 커넥션 풀 부족 에러가 발생하는지 확인합니다.
    *   **캐시 복구 속도:** 캐시 미스가 발생한 요청들이 빠르게 DB 조회를 거쳐 Redis에 캐시를 성공적으로 재적재하는지 검증합니다.

### 2. 성능 한계 검증 (Stress & Scalability Test)

시스템이 붕괴되는 임계점을 파악하고 인프라 스케일링 정책을 수립하기 위한 한계 테스트입니다.

#### ① DB 파티셔닝 성능 한계 검증
*   **방법:** 테스트용 데이터베이스에 수년 치에 해당하는 대량의 모의 데이터(예: 수백만 건의 Intent, Message 기록)를 채워 넣습니다.
*   **검증 사항:**
    *   **파티션 프루닝(Pruning):** `term = '202610'`과 같은 조건절이 포함된 쿼리가 전체 파티션을 스캔하지 않고 대상 파티션만 좁혀 조회하는지 실행 계획(Explain)을 확인합니다.
    *   **인덱스 효율성:** 대용량 테이블 상태에서 `idx_message_room_id_pagination` 및 `idx_read_status_member` 인덱스가 제 기능을 발휘하여 페이징 조회가 100ms 이하로 유지되는지 검증합니다.

#### ② 내구성 및 메모리 누수 검증 (Endurance Test)
*   **방법:** 피크타임 트래픽의 약 50~70% 수준의 부하를 최소 수 시간에서 반나절 이상 지속해서 인가합니다.
*   **검증 사항:**
    *   **JVM GC 및 메모리:** 탐색용 방향 그래프 구조를 메모리 내에 유지하면서 연산하는 경우, 가비지 컬렉션(GC)이 효율적으로 일어나며 메모리 누수(Memory Leak)가 발생하지 않는지 확인합니다.
    *   **Redis 메모리 사용량:** 캐시 데이터 누적으로 인해 Redis 메모리가 한계에 도달하지 않는지, 설정된 TTL(10분) 정책에 따라 만료된 캐시가 적절히 제거되는지 관찰합니다.

### 3. 모니터링해야 할 핵심 시스템 지표

부하 테스트를 진행하는 동안 관제 도구(APM, Grafana, AWS CloudWatch 등)를 통해 집중적으로 모니터링해야 하는 지표들입니다.

| 컴포넌트 | 수집 및 관찰 지표 | 비고 |
| :--- | :--- | :--- |
| **API 서버** | **TPS (초당 처리량), 응답 지연 시간(p95/p99 Latency), CPU/메모리 점유율, active thread 수** | 5초 폴링에 대응하는 서블릿 쓰레드 포화 여부 확인 |
| **Database** | **CPU/Memory 사용량, Active Connections, Lock Wait Time, Write IOPS, Slow Query 발생 빈도** | 캐시 미스 시 유입되는 복합 조인 쿼리 성능 확인 |
| **Redis** | **CPU 사용량, Used Memory, Connected Clients, Cache Hit Rate, Evicted Keys** | 캐시 성능 지표의 핵심 요소 |
| **비동기 큐** | **Queue Depth (대기 중인 이벤트 수), Event Processing Time (이벤트 소비 시간)** | 사이클 탐색 엔진 병목 여부 파악 |
