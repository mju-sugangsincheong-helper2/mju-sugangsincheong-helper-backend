제시해주신 설계 문서와 비즈니스 흐름을 기반으로, 시스템의 정합성과 안정성을 검증하기 위해 수행해야 할 **단위 테스트(Unit Test) 시나리오 목록**을 정리해 드립니다. 

각 기능의 정상 흐름뿐만 아니라 복잡한 상태 전이 규칙, 동시성 이슈, Redis 캐시 일관성 검증을 포함하고 있습니다.

### 1. INTENT 등록 및 검증 관련 테스트

사용자가 교환 의사를 등록하는 시점의 입력값 검증과 데이터 적재, 그리고 비동기 이벤트 발행 흐름을 검증합니다.

*   **[정상 흐름] 신규 교환 의사 등록 성공**
    *   **Given:** 특정 학기(`term`), 사용자, 버릴 과목(`give_course_no`), 원하는 과목(`want_course_no`) 입력
    *   **When:** 등록 API를 호출하여 저장 시도
    *   **Then:** `EXCHANGE_INTENT`에 데이터가 적재되고, `is_deleted`는 `FALSE`, `deleted_at`은 `NULL`로 저장됨을 확인. 이후 사이클 탐색 비동기 이벤트가 올바른 파라미터(`term` 등)를 물고 발행되는지 검증
*   **[예외 흐름] 비정상 과목 식별자 검증**
    *   **Given:** 숫자가 아닌 문자열이나 모호한 과목명(예: "운영체제", "OS-12")을 입력값으로 전달
    *   **When:** 등록 요청 진행
    *   **Then:** 비즈니스 벨리데이션에 의해 예외가 발생하고 등록에 실패함을 확인
*   **[예외 흐름] 동일 과목 교환 요청 차단**
    *   **Given:** 버릴 과목 번호와 원하는 과목 번호를 동일하게 설정하여 등록 시도 (예: `10023` -> `10023`)
    *   **When:** 등록 요청 진행
    *   **Then:** 자체 유효성 검증을 통해 차단되고 예외를 반환하는지 확인
*   **[캐시 제어] 등록 후처리 동작 검증**
    *   **Given:** 신규 Intent 등록 트랜잭션이 커밋됨
    *   **When:** 캐시 갱신 로직 작동
    *   **Then:** 
        *   `exchange::{term}:feed:cache` 목록 맨 앞에 신규 항목이 추가(LPUSH)되고, 크기가 50개를 초과할 시 마지막 항목이 잘려 나가는지(LTRIM) 확인
        *   해당 사용자의 `exchange::{term}:member:{member_id}:intents:cache` 캐시가 정상적으로 제거(Evict)되는지 확인

### 2. 그래프 사이클 탐색 관련 테스트

메모리 내 방향 그래프를 빌드하고, 닫힌 고리(Cycle)를 찾아내는 탐색 알고리즘의 정확성을 검증합니다.

*   **[정상 흐름] 2자 간 직관적 사이클 탐색**
    *   **Given:** 매칭 풀에 2개의 Intent가 존재 (`UserA: 101 -> 102`, `UserB: 102 -> 101`)
    *   **When:** 사이클 탐색 알고리즘 실행
    *   **Then:** 두 사용자가 묶인 1개의 사이클을 올바르게 감지함을 확인
*   **[정상 흐름] 다자 간 순환 사이클 탐색**
    *   **Given:** 매칭 풀에 3개의 Intent가 존재 (`UserA: 101 -> 102`, `UserB: 102 -> 103`, `UserC: 103 -> 101`)
    *   **When:** 사이클 탐색 알고리즘 실행
    *   **Then:** 3명이 포함된 하나의 순환 사이클을 정상적으로 찾아내는지 확인
*   **[예외 흐름] 삭제된 카드 배제**
    *   **Given:** 사이클이 형성되는 조건이나, 그중 한 카드가 이미 철회 상태(`is_deleted = TRUE`)인 경우
    *   **When:** 사이클 탐색 실행
    *   **Then:** 해당 카드를 간선(Edge)에서 제외하여 사이클이 생성되지 않음을 확인
*   **[예외 흐름] 비순환 구조 탐색 제외**
    *   **Given:** 체인 형태로 꼬리를 물고 있으나 마지막이 닫히지 않은 경우 (예: `A: 101 -> 102`, `B: 102 -> 103`, `C: 103 -> 104`)
    *   **When:** 사이클 탐색 실행
    *   **Then:** 어떠한 사이클도 반환하지 않음을 검증

### 3. 방 생성 및 동시성 관련 테스트

순환 고리가 발견되었을 때, 다수의 연관 테이블에 데이터가 정합성 있게 생성되는지 및 동시성 충돌 처리를 검증합니다.

*   **[정상 흐름] 방 생성 및 참여 관계 초기화**
    *   **Given:** 탐색 엔진이 신규 사이클을 전달함 (참여자 A, B, C)
    *   **When:** 방 생성 트랜잭션 수행
    *   **Then:** 
        *   `EXCHANGE_ROOM`에 고유 `cycle_hash`(오름차순 정렬 후 해싱)와 함께 방 레코드가 생성됨
        *   `EXCHANGE_ROOM_INTENT`에 참여자 3명의 매핑 정보가 삽입됨 (`is_deleted = FALSE`, `is_on = TRUE`)
        *   `EXCHANGE_ROOM_MESSAGE`에 최초 시스템 웰컴 메시지가 삽입됨
        *   `EXCHANGE_ROOM_READ_STATUS`에 각 멤버별 읽음 정보가 삽입되고, `last_read_message_id`가 해당 웰컴 메시지 ID로 초기화됨
*   **[동시성 검증] 중복 방 생성 방지**
    *   **Given:** 동일한 `cycle_hash`를 가진 방 생성이 거의 동시에 2번 요청됨 (Race Condition 상황)
    *   **When:** 데이터 삽입 시도
    *   **Then:** 데이터베이스 유니크 제약 조건(`uniq_term_cycle_hash`) 및 `ON CONFLICT DO NOTHING` 처리에 의해 하나의 방만 생성되고 다른 요청은 부드럽게 무시되거나 정상 종료됨을 확인
*   **[동시성 검증] 트랜잭션 중 카드 취소 발생**
    *   **Given:** 방 생성 로직 시작과 동시에, 참여자 중 한 명이 자신의 Intent를 취소하는 요청을 보냄
    *   **When:** 방 생성 로직 내에서 `SELECT FOR UPDATE`로 각 Intent 레코드의 락을 확보하고 검증함
    *   **Then:** 카드 상태가 도중에 변경되었음을 감지하여 방 생성 트랜잭션이 안전하게 롤백되거나 취소됨을 확인
*   **[캐시 제어] 방 생성 후처리 동작 검증**
    *   **Given:** 방 생성 트랜잭션이 최종 커밋됨
    *   **When:** 캐시 비우기 수행
    *   **Then:** 사이클에 포함되어 방에 참여하게 된 **멤버 전원**의 `exchange::{term}:member:{member_id}:rooms:cache`가 정상적으로 삭제(Evict)되는지 검증

### 4. INTENT 삭제 및 대화방 상태 엔진 관련 테스트

사용자가 교환 카드를 취소할 때, 관련 대화방에 미치는 연쇄 영향과 방 상태 전이 엔진의 상태값 계산 로직을 검증합니다.

*   **[정상 흐름] 의사 철회 및 매핑 동기화**
    *   **Given:** 사용자가 본인의 특정 `intent_id`를 삭제 요청함
    *   **When:** 삭제 트랜잭션 실행
    *   **Then:** 
        *   `EXCHANGE_INTENT`의 해당 행이 `is_deleted = TRUE`로 마킹되고 삭제 일시가 기록됨
        *   역방향 인덱스를 타서 해당 사용자가 속해 있던 모든 대화방 매핑 정보(`EXCHANGE_ROOM_INTENT`) 내의 `is_deleted`가 `TRUE`로, `is_on`이 `FALSE`로 수정됨을 확인
*   **[상태 엔진] 2자 간 대화방에서 1명 이탈 (잔여 2인 미만)**
    *   **Given:** 원래 2명으로 구성되어 있던 대화방에서 멤버 A가 카드를 삭제함 ($N=2, D=1$)
    *   **When:** 상태 엔진 작동 ($N-D = 1 < 2$)
    *   **Then:** 해당 방의 `EXCHANGE_ROOM.is_active`가 `FALSE`로 변하고, 전체 방 상태(Status)가 `ALL_DELETE`로 전환되는지 확인
*   **[상태 엔진] 3자 간 대화방에서 1명 이탈 (잔여 2인 이상)**
    *   **Given:** 3명으로 구성된 순환 대화방에서 멤버 A가 카드를 삭제함 ($N=3, D=1$)
    *   **When:** 상태 엔진 작동 ($N-D = 2 \ge 2$)
    *   **Then:** 방 자체는 활성 상태를 유지하되, 방 상태(Status)가 `PARTIAL_DELETE`로 전환되는지 확인
*   **[시스템 알림] 이탈 안내 메시지 확인**
    *   **Given:** 누군가 카드를 삭제하여 방 상태가 업데이트됨
    *   **When:** 트랜잭션 내에서 이탈 알림 처리
    *   **Then:** 해당 방(`EXCHANGE_ROOM_MESSAGE`)에 "OOO님이 교환 의사를 취소하여 방이 비활성화되었습니다" 또는 "일부 사용자가 이탈하였습니다" 등의 안내 메시지가 올바르게 저장되는지 검증
*   **[캐시 제어] 삭제 후처리 동작 검증**
    *   **Given:** 삭제 트랜잭션 성공적으로 커밋됨
    *   **When:** 후처리 캐시 삭제 로직 실행
    *   **Then:** 
        *   본인의 `intents:cache`가 정상적으로 제거(Evict)되는지 확인
        *   영향을 받은 대화방에 소속되어 있던 **참여자 전원**의 `rooms:cache`가 제거되는지 확인

### 5. 방 ON/OFF 토글 및 상태 엔진 관련 테스트

사용자가 방을 목록에서 숨기거나 알림을 끌 때 개별 설정 변경 및 방의 전체 유효성 상태 전이 규칙을 검증합니다.

*   **[정상 흐름] 개인 토글 상태 반영**
    *   **Given:** 사용자가 특정 방을 숨김(OFF) 처리하고자 함
    *   **When:** 토글 API 호출
    *   **Then:** `EXCHANGE_ROOM_INTENT` 테이블의 해당 사용자 행에서 `is_on = FALSE`로 정확하게 반영됨을 확인
*   **[상태 엔진] 토글에 따른 방 상태 전이 검증 (N, D, O, A 규칙 검증)**
    *   **Case 1 (규칙 A - 인원 부족):** 삭제된 의사 등으로 인해 실질 활성자가 2명 미만이 될 때 $\rightarrow$ 방 상태가 `ALL_DELETE`로 전이되는지 검증
    *   **Case 2 (규칙 B - 일부 삭제):** 실질 활성자는 2인 이상이나 이미 삭제된 의사가 존재할 때 ($D > 0$) $\rightarrow$ 방 상태가 `PARTIAL_DELETE`로 전이되는지 검증
    *   **Case 3 (규칙 C - 일부 꺼짐):** 삭제된 카드는 없으나($D = 0$), 최소 1명 이상의 참여자가 방을 OFF 했을 때 ($O > 0$) $\rightarrow$ 방의 상태가 `PARTIAL_OFF`로 전이되어 다른 이에게 노출될 준비를 하는지 검증
    *   **Case 4 (규칙 D - 완전 활성):** 아무도 삭제하지 않았고 모두가 알림 활성 상태일 때 ($D = 0, O = 0$) $\rightarrow$ 방 상태가 `ACTIVE`로 전환되는지 검증
*   **[목록 필터링] 폴링 노출 배제 검증**
    *   **Given:** 사용자가 방 A는 `is_on = TRUE`로 두고, 방 B는 `is_on = FALSE`로 설정함
    *   **When:** 사용자의 방 목록 조회 쿼리(혹은 폴링 API)를 구동함
    *   **Then:** DB 인덱스 조건(`idx_room_intent_member`)에 의해 `is_on = FALSE` 처리된 방 B는 결과 목록에서 완벽하게 제외됨을 검증

### 6. 채팅 메시지 및 읽음 상태(배지) 관련 테스트

메시지를 발송하거나 읽을 때, 실시간 읽음 위치 지시자(Pointer)의 이동과 미읽음 카운트가 동기화되는지 검증합니다.

*   **[정상 흐름] 메시지 전송 및 발신자 읽음 위치 갱신**
    *   **Given:** 사용자가 대화방에서 메시지를 작성함
    *   **When:** 메시지 전송 로직 수행
    *   **Then:** 
        *   `EXCHANGE_ROOM_MESSAGE`에 새 텍스트가 정상 삽입됨
        *   발신자 본인의 `EXCHANGE_ROOM_READ_STATUS.last_read_message_id`가 방금 생성된 메시지의 ID로 즉각 갱신됨을 확인
*   **[정상 흐름] 메시지 조회 및 수신자 읽음 상태 최신화**
    *   **Given:** 대화방에 아직 수신자가 읽지 않은 새 메시지가 쌓여 있는 상태
    *   **When:** 수신자가 채팅방 메시지 내역을 조회(진입 혹은 페이지 스크롤)함
    *   **Then:** 수신자의 `EXCHANGE_ROOM_READ_STATUS` 테이블 내 `last_read_message_id`가 해당 방의 가장 최신 메시지 ID로 수정되고, 미읽음 카운트가 `0`으로 리셋됨을 검증
*   **[정상 흐름] 미읽음 메시지 수 정확도 검증**
    *   **Given:** 특정 방에 총 10개의 메시지가 있으며, 사용자의 `last_read_message_id`가 7번 메시지를 가리키고 있음
    *   **When:** 유저 방 목록 요약 정보를 조회/계산함
    *   **Then:** 해당 사용자의 안 읽은 메시지 수(`unread_count`)가 정확히 `3`으로 반환되는지 확인

### 7. Redis 캐시 제어 및 복구 관련 테스트

각 API 호출 후 캐시 무효화(Evict)가 잘 작동하는지, 캐시가 없는 상태에서 조회 요청 시 DB를 통해 올바른 데이터 구조로 캐시가 자동 복구(Reconstruct)되는지 검증합니다.

*   **[캐시 미스 복구] 최근 교환 의사 피드 (CACHE 1) 복구**
    *   **Given:** Redis 내 `exchange::{term}:feed:cache` 키가 만료되거나 삭제된 상태
    *   **When:** 피드 조회 요청 유입
    *   **Then:** DB에서 아직 유효한 최신 Intent 데이터를 최대 50개 조회해 캐시에 다시 적재하고 동일한 데이터를 응답하는지 검증
*   **[캐시 미스 복구] 유저별 활성 Intent 목록 (CACHE 2) 복구**
    *   **Given:** `exchange::{term}:member:{member_id}:intents:cache` 키가 존재하지 않는 상태
    *   **When:** 메인 화면 조회 요청 유입
    *   **Then:** DB에서 해당 유저의 미삭제 카드 목록을 뒤져 캐시에 정상적으로 써넣는지 검증
*   **[캐시 미스 복구] 유저별 방 목록 요약 (CACHE 3) 복구**
    *   **Given:** `exchange::{term}:member:{member_id}:rooms:cache` 키가 존재하지 않는 상태
    *   **When:** 메인 화면 조회 및 폴링 요청 유입
    *   **Then:** 복잡한 집계 쿼리(가장 최신 메시지 내용, 마지막 메시지 일시, 미읽음 메시지 카운트 등)가 정상 구동되어 계산된 데이터 구조 그대로 캐시가 빌드되는지 검증
